## 4. [CALIBRATE] Manifest `captured_at` vs. internal timestamp — measured on all 94 files

Method: for every evidence file, compare `evidence_files.csv`'s `captured_at` against the timestamp(s) found inside the file (SQL header `Captured at` or `snapshot_scope` rows; JSON `exported_at`/`captured_at`/`snapshots[].captured_at`; the `.txt` file's `Snapshot:` line; for logs, the latest in-file event timestamp as a bounds check — logs have no single internal "captured_at" field).

**Result: 94 of 94 files are internally consistent, but 12 of them are not "single timestamp" files:**

- **SQL (24/24) — exact agreement.** Every two-table file's header `Captured at` equals the manifest. Every inventory file's `snapshot_scope.captured_at` (for every `origin_system` row) equals the manifest.
- **JSON, non-bundle families (16/16) and the `.txt` file — exact agreement.** The single `exported_at`/`captured_at`/`Snapshot:` value always equals the manifest `captured_at`.
- **Logs (26/26) — bounds check only, no violation.** The latest in-file event timestamp is always `<=` the manifest `captured_at` (a log export's own last line is never after the file was "captured").
- **JSON, `customer_data_snapshot_bundle_*` family (12/12) — top-level `exported_at` always equals the manifest, but each of the file's `snapshots[]` carries its own, *earlier*, per-snapshot `captured_at`.** Example (`evidence_02`, manifest/`exported_at` = `2026-09-17T12:00:00Z`): one nested snapshot's `customer_profiles` collection is stamped `2026-09-09T12:00:00Z`, another `customer_search_documents` snapshot is stamped `2026-09-15T09:00:00Z`, and three more collections are stamped `2026-09-15T12:00:00Z` — all strictly before the bundle's own `exported_at`/manifest value. The same pattern repeats across all 12 bundle files (2–4 distinct per-snapshot times each, always `<=` the bundle's `exported_at`).

**This is not a data inconsistency — it is a structural fact the Phase 2 evidence parser must handle correctly:** the bundle's own `exported_at` (= manifest `captured_at`) only says when the *bundle was packaged*; the true "when was this specific record actually observed" time is the **per-snapshot `captured_at` inside it**, which can be up to several days earlier.

**Decision needed from the user before Phase 2 (do not want to guess this):** should `code/audit/evidence/json_parser.py` build each `Observation`'s `captured_at` from the **per-snapshot inner timestamp** (finer-grained, lets more evidence be used for early `audit_at` cases) rather than from the file's own manifest/`exported_at` (coarser, would under-use evidence that was genuinely captured earlier but bundled later)? `code/audit/timeview.py`'s `TimeView.is_visible(timestamp)` already supports either choice — it is a generic gateway callable with any timestamp a parser extracts, including a per-snapshot one — so no rework is needed either way; this only decides which timestamp the Phase 2 JSON parser passes in for bundle-family records. Recommendation: use the per-snapshot timestamp, since PRD §7.2 ("for each `snapshot`, record `captured_at`...") already implies per-snapshot granularity. **Awaiting confirmation.**

## 8. SQL sandbox allowlist (derived empirically, implemented in `code/audit/evidence/sql_sandbox.py`)

**Load-time** (building the in-memory database from the file): `CREATE_TABLE`, `CREATE_INDEX`, `INSERT`, `PRAGMA` (only `foreign_keys`), `TRANSACTION`, `READ`, `REINDEX`, `FUNCTION` (only `json_valid`), `UPDATE` (only on `sqlite_master`, SQLite's own internal side effect of creating a `PRIMARY KEY`/`UNIQUE` index — never a real table). Everything else is denied, including `ATTACH`, `DETACH`, `CREATE_TRIGGER`, `CREATE_VIEW`, `CREATE_VTABLE`, and `RECURSIVE`.

**Query-time** (after the connection is handed back to calling code): re-armed with a strictly smaller allowlist — `SELECT`/`READ`/`TRANSACTION` and the same small `FUNCTION` set (`json_valid`, `json_extract`, `count`, `max`, `min`, `sum`, `avg`, `length`, `lower`, `upper`, `coalesce`). `INSERT`/`UPDATE`/`DELETE`/`DROP`/`ATTACH` are all denied at this stage too, so nothing — including a bug in later audit code — can mutate evidence after it is loaded.

Verified against 8 hostile inputs (`ATTACH`, a writable `PRAGMA`, `CREATE TRIGGER`, `load_extension`, `CREATE VIEW`, `WITH RECURSIVE`, an oversized statement count, a denied function): all 8 rejected safely with no file or network side effect (see `code/tests/test_sql_sandbox.py`).
